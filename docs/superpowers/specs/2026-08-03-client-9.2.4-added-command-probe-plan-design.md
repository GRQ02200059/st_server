# Client 9.2.4 Added-Command Probe Plan Design

- Date: 2026-08-03
- Active client: `9.2.4`
- Baseline client: `9.2.2`
- Scope: the 63 command IDs added by 9.2.4
- Decision: use the recommended option under the user's standing
  authorization to proceed without interactive confirmation.

## Goal

Produce a reproducible, reviewable probe plan for the commands added in client
9.2.4. The plan must separate literal, read-only requests that can be sent
automatically from commands that mutate account state, control a scene, need
live identifiers, are server pushes, or have unresolved static call sites.

This work prepares official-server capture. It does not send a game command,
guess a response, or add private-server response behavior.

## Context

The active inventory contains 2,655 commands and 2,409 remain
`UNIMPLEMENTED`. The Android package is installed, but the game process is
absent. The host listener, HTTP service, ADB reverse, and passive autosave are
ready; official probing cannot resume until the client reconnects naturally.

Static review of the 63 added IDs found materially different risks:

- `3720`, `3913`, `4383`, `4385`, `4386`, and `6148` are literal read-only
  queries.
- `6156` is a literal read-only query whose wire request is JSON `null`.
- `2634`, `4387`, `4991`, `6128`, `6131`, and `6157` are read-only but need
  live world, hero, server, state, or search inputs.
- Reward, purchase, sign-up, selection, speedup, deployment, sell, collect,
  and pin commands mutate official account state.
- Several constants have no resolved request site in the decompiled build and
  must remain unresolved rather than inferred from their names.

## Options

### Selected: explicit versioned manifest plus validator

Store one JSON row for every added command. Each row records its inventory
name, classification, static request shape, optional literal probe payload,
source references, and rationale. A Python validator proves that the manifest
exactly covers the 9.2.4-minus-9.2.2 ID set and exports only eligible rows.

This approach is deliberately conservative: source review supplies the safety
decision, while code enforces completeness and export invariants.

### Rejected: manual Markdown checklist only

A document is easy to read but cannot prove that every added ID is covered or
prevent an unsafe row from entering a batch file.

### Rejected: automatic safety inference from names or C# regexes

Names such as `GET`, `QUERY`, and `REWARD` do not fully determine side effects.
The decompiled send syntax also includes nested generics and indirect helpers
that the current inventory regex does not resolve. Automatic inference would
turn scanner gaps into unsafe claims.

## Artifacts

### Manifest

`tools/protocol/client-9.2.4-added-command-probes.json` has:

```json
{
  "clientVersion": "9.2.4",
  "baselineVersion": "9.2.2",
  "commands": [
    {
      "id": 3720,
      "names": ["QUERY_UNION_WEIXIN_GROUP_INFO"],
      "classification": "READ_ONLY_STATIC",
      "requestShapes": ["[]"],
      "probePayload": [],
      "autoProbe": true,
      "evidence": [
        "Game.UI.GamePlay/Tenth.UI/UnionMainUI.cs:348-352"
      ],
      "reason": "Queries the current union Weixin-group state."
    }
  ]
}
```

Allowed classifications are:

- `READ_ONLY_STATIC`: read-only and has a literal payload.
- `READ_ONLY_CONTEXTUAL`: read-only but requires current client state.
- `MUTATING`: can change account, alliance, activity, inventory, reward, army,
  market, or preference state.
- `SESSION_CONTROL`: changes scene or matching/session state.
- `SERVER_PUSH`: observed only as a receive path.
- `UNRESOLVED`: no complete static request contract was found.

`probePayload` is present only for a literal wire value. `null` is a valid
literal payload and is distinct from an absent field.

### Validator and exporter

`tools/client_protocol_probe_plan.py` exposes pure validation and batch-build
functions plus a CLI. It consumes:

1. The preserved 9.2.2 inventory.
2. The active 9.2.4 inventory.
3. The versioned probe manifest.

Validation fails unless:

- manifest versions match the supplied inventories;
- manifest IDs exactly equal `current IDs - baseline IDs`;
- IDs are sorted and unique;
- names exactly match the active inventory;
- every row has an allowed classification, non-empty evidence, request-shape
  list, and reason;
- `autoProbe=true` is used only with `READ_ONLY_STATIC`;
- every automatic row contains `probePayload`, including explicit JSON null;
- non-automatic rows cannot leak into the exported batch.

The exporter writes the existing `capture_send.py` shape:

```json
[
  {"cmd": 3720, "payload": []},
  {"cmd": 3913, "payload": []}
]
```

It does not open ADB, WebSocket, HTTP, or network connections.

## Initial Automatic Batch

The initial automatic batch is intentionally limited to:

| Cmd | Payload | Static basis |
|---:|---|---|
| `3720` | `[]` | union Weixin-group query |
| `3913` | `[]` | self family-fame query |
| `4383` | `[0, 10]` | first record-list page |
| `4385` | `[]` | market/recruit snapshot query |
| `4386` | `[]` | last-record query |
| `6148` | `[]` | family qualification query |
| `6156` | `null` | collected-family list query |

These commands are exported but not sent while `phoneConnected=false`.
Contextual reads remain manual until their live arguments are obtained from
passively captured client state.

## Runtime Use

The PipeBridge Web service keeps passive autosave enabled before any active
probe. When the client reconnects naturally:

1. Archive naturally emitted packets first.
2. Revalidate and export the automatic batch from committed evidence.
3. Check `phoneConnected=true` immediately before sending.
4. Send one command at a time and retain both send and receive events.
5. Stop the batch on disconnect, timeout, Bridge error, or an unexpected
   mutation signal.
6. Import only 9.2.4 captures into 9.2.4 evidence.

No command outside the exported batch is eligible for unattended sending.

## Tests

Python tests use temporary inventories and manifests to prove:

- exact delta coverage and deterministic ordering;
- version and name mismatch rejection;
- duplicate and missing ID rejection;
- classification and evidence validation;
- explicit JSON-null payload preservation;
- unsafe automatic-row rejection;
- exported rows contain only `cmd` and `payload`;
- both module and direct test entrypoints work.

The final gate also runs `git diff --check`. No Kotlin test is needed because
this subtask changes no server runtime behavior.

## Non-Goals

- Starting or restarting the Android client.
- Sending commands while the client process is absent.
- Automatically probing contextual or mutating commands.
- Inferring official response bodies from static consumers.
- Adding server handlers without captured response evidence.
- Reclassifying the historical 9.2.2 capture index as 9.2.4 evidence.
