# 五星武将与 S/A 战法完整引擎设计

## 目标

将当前只覆盖少量手写战法与常见效果的战斗实现，升级为配置驱动的完整战法引擎。验收范围为：

- 客户端 `hero_table.csv` 中所有 `quality_name=五星` 武将的自带战法。
- 服务端玩家战法库 `SkillInventoryCatalog` 中，客户端 `skill_table.csv` 标记为 S 或 A 级的可见、可学习主战法。
- 上述主战法直接或间接引用的全部子战法和派生效果。

按当前客户端 dump 与服务端战法库计算，验收清单包含：

- 308 个主战法，其中 234 个五星武将自带战法、83 个可学习 S/A 战法，二者重叠 9 个。
- 668 个包含子战法在内的执行节点。
- 112 种实际使用的效果类型。
- 1935 条战法效果明细。

统计清单由测试从配置动态生成，数字用于锁定当前 dump 的验收基线。以后替换客户端配置时，新增的目标战法和依赖必须显式进入覆盖报告，不能静默跳过。

## 非目标

- 不单独实现或验收低星武将自带战法。
- 不单独实现 B、C、D 级可学习战法。
- 不把 NPC、活动、剧情或不可见赛季派生战法作为主战法验收对象。
- 目标战法依赖这些内部战法时，仍必须实现对应执行节点。
- 本期不实现战斗动画；只保证战斗逻辑、兵损、胜负与客户端文字战报数据正确。

## 总体架构

战法系统作为一个深模块存在，战斗引擎只依赖两个入口：

```kotlin
prepareBattle(context): List<BattleEvent>
trigger(trigger: BattleTrigger, context: BattleContext): List<BattleEvent>
```

`prepareBattle` 负责被动、指挥和战前预备效果。`trigger` 负责正式战斗中的各类触发点。目标选择、状态冲突、子战法调用和战报事件都隐藏在模块内部，避免继续把战法分支堆进 `BattleEngine`。

模块内部由四层组成。

### SkillCatalog

从 `skill_table.csv`、`skill_detail_table.csv` 和 `skill_effect_table.csv` 读取战法配置，构造不可变规则图。

职责包括：

- 构建主战法、效果明细与子战法依赖。
- 标准化战法类型、发动率、准备回合、距离、目标、条件和持续参数。
- 检测缺失依赖、循环依赖、无主明细和未知效果。
- 生成本次配置的验收清单与覆盖报告。

启动或测试阶段发现规则图损坏时必须明确失败，错误信息包含战法 ID、明细 ID、效果 ID 和依赖路径。

### SkillRuleInterpreter

解释规则图并执行通用战法语义。

职责包括：

- 发动率、士气、战法发动率加成和次数限制。
- 准备、冷却、延迟回合、延迟次数和准备打断。
- 目标阵营、攻击距离、目标数量、随机选择、站位选择、兵力或属性排序以及状态筛选。
- 物理伤害、策略伤害、持续伤害、恢复和属性变化。
- 条件、前置条件、施放条件和子战法递归调用。
- 从执行结果直接产生结构化战斗事件。

解释器不得依赖客户端文字描述猜测规则；文字只允许用于诊断信息。

### BattleEffectRegistry

112 种目标效果各自注册处理器。处理器通过统一接口读取效果定义、战斗上下文和目标，返回状态变化与战斗事件。

效果实例必须保存：

- 来源武将与来源战法。
- 来源战法类型。
- 效果 ID、冲突组和强度。
- 剩余回合或剩余次数。
- 叠加层数与最大层数。
- 是否可清除、绑定效果与延迟信息。

覆盖、替换和叠加由客户端字段 `buff_type`、`replace_type`、`bind_flag`、`add_count_max`、`available_round`、`available_hit` 和 `clear_per_hit` 决定，不能使用“同状态直接追加”的简化规则。

### SpecialSkillPlugin

只处理 CSV 字段无法完整表达的特殊机制，例如复杂的跨目标联动、按历史事件回放、动态替换战法或特殊伤害转移。

每个插件：

- 按战法 ID 或明确的特殊效果 ID 注册。
- 使用与解释器相同的 `BattleContext`、状态仓库、随机源和事件输出。
- 不能直接写客户端战报字符串。
- 必须有独立语义测试和一条完整战斗测试。

现有 `LegacySkillCatalog` 中能由配置表达的手写逻辑将迁移到解释器；真正特殊的部分转为插件。一个战法只能有一个权威执行路径。

## 战斗阶段与触发点

阶段顺序固定为：

1. 被动战法。
2. 指挥战法和战前预备效果。
3. 正式回合开始。
4. 回合开始效果。
5. 武将行动前。
6. 主动战法。
7. 普通攻击。
8. 追击战法。
9. 行动后。
10. 回合结束。

引擎提供以下通用触发点：

- `BATTLE_PASSIVE`
- `BATTLE_COMMAND`
- `ROUND_START`
- `ACTION_BEFORE`
- `ACTIVE_SKILL_ATTEMPT`
- `NORMAL_ATTACK_BEFORE`
- `NORMAL_ATTACK_AFTER`
- `DAMAGE_BEFORE`
- `DAMAGE_AFTER`
- `HURT_AFTER`
- `PURSUIT_ATTEMPT`
- `ACTION_AFTER`
- `ROUND_END`
- `BASE_HERO_DEFEATED`

配置解释器和特例插件只能响应触发点，不能改变全局阶段顺序。

## 准备战法

准备战法保存已选择的战法和执行上下文快照，完成时不重复判定首次发动率。

- 混乱和犹豫会取消当前准备。
- 跳过准备回合的效果可立即完成或减少剩余准备回合。
- 同一战法准备期间不能重复加入准备队列。
- 准备被取消、完成或替换时必须产生对应结构化事件。
- 准备完成后的目标选择遵循该战法的客户端配置；需要在准备时锁定目标的特殊机制由插件实现。

## 目标选择

目标解析覆盖：

- 自己、友军、我军、敌军和任意单位。
- 单体、群体和全体。
- 攻击距离与战法有效距离。
- 指定大营、中军、前锋或位置集合。
- 最低/最高兵力、攻击、防御、谋略、速度等属性。
- 已具有或未具有指定状态。
- 随机不重复选择。
- 阵亡目标排除以及允许阵亡目标的特殊恢复规则。

随机选择只使用注入的 `BattleRandom`，保证同一随机种子可复现。

## 条件与次数

解释器支持 `cast_condition`、`precondition`、`condition`、`available_hit`、`delay_round`、`delay_hit` 和 `clear_per_hit`。

条件至少覆盖：

- 当前回合和回合区间。
- 自己或目标兵力比例。
- 当前状态与控制状态。
- 本回合或累计普攻、主动、追击、受伤和造成伤害次数。
- 战法是否发动、是否准备、是否命中。
- 目标数量、阵亡情况和大营存活状态。

未知条件不能默认为真。开发和测试环境直接报错；正式运行记录完整诊断并跳过该条效果。

## 子战法

效果 122、123 以及配置中明确引用战法 ID 的字段通过规则图递归执行。

- 子战法继承原始来源武将、主战法、战法类型和战报上下文。
- 子战法可覆盖自己的目标、概率和条件。
- 调用栈记录完整依赖路径。
- 设置循环检测和最大深度保护；触发保护时测试失败，正式运行记录错误并终止该调用分支。

## 数值计算

普通攻击、物理战法、策略战法和持续伤害统一使用 `BattleDamageCalculator`。恢复使用独立但同样统一的恢复计算模块。

计算输入包括：

- 当前兵力与兵力上限。
- 攻击、防御、谋略和速度。
- 战法倍率及属性成长参数。
- 兵种、阵营、称号、队伍和装备修正。
- 造成伤害、受到伤害、普通、主动、追击、物理和策略分类修正。
- 士气和客户端配置的倍率上限。

所有修正按明确分类结算，不能把属性增减、伤害增减和受到伤害增减混为同一状态。

恢复只能恢复伤兵，不得超过伤兵量、存活兵力上限或配置允许的特殊上限。

## 胜负与结算

- 任一方大营兵力降为 0 时立即结束战斗。
- 八个正式回合结束且双方大营存活时为平局。
- 服务端保存真实剩余兵力，包括 0 兵，不强制保留 1 兵。
- 只有最终结果为进攻方胜利时才占领土地。
- 多队守军必须逐队结算；上一队结算后的进攻方兵力传入下一队。

## 战报

战法执行模块只产生结构化 `BattleEvent`。客户端适配层负责把事件编码为客户端动作，不补造伤害、状态或胜负。

必须表达：

- 被动、指挥、主动和追击的发动。
- 准备开始、取消和完成。
- 普攻、物理伤害、策略伤害和持续伤害。
- 恢复、属性变化、控制、增减伤、规避、洞察和状态消失。
- 每个武将行动开始与结束。
- 回合、最终兵力和真实胜负。

不要求动画帧或播放时长与官方一致。

## 错误处理

开发和测试环境采用严格模式：

- 未知效果、未知条件或未知选择器直接失败。
- 断开的子战法、循环依赖和无事件主战法直接失败。
- 目标范围内出现 `UnsupportedSkillEffect` 直接失败。

正式运行采用安全模式：

- 记录战法 ID、明细 ID、效果 ID、字段值、触发点和调用栈。
- 只跳过无法执行的效果分支。
- 不生成虚假伤害、恢复、恐慌或其他替代效果。
- 战斗仍能完成并生成可解析战报。

## 测试与覆盖率

### 清单测试

- 当前配置必须得到 308 个主战法、668 个执行节点、112 种效果和 1935 条明细。
- 每个目标主战法必须存在配置和执行入口。
- 所有依赖必须可达且无循环。

### 效果级测试

每种效果至少验证：

- 目标与阵营。
- 数值计算。
- 持续回合或次数。
- 覆盖、替换与叠加。
- 清除与免疫。
- 结构化事件和客户端战报动作。

### 战法级测试

每个主战法至少有一条确定性完整战斗测试，验证发动阶段、目标和核心结果。同名赛季变体使用参数化测试验证参数差异。

测试不能只验证“不抛异常”；必须至少断言一个有意义的状态、兵力、属性、触发顺序或战报结果。

### 组合测试

至少覆盖：

- 准备被混乱或犹豫打断。
- 洞察与控制、规避与无视规避。
- 连击触发两次普攻和追击。
- 持续伤害的覆盖、刷新与结算。
- 恢复与伤兵上限。
- 同类增减伤冲突。
- 子战法递归、延迟和次数限制。
- 大营阵亡立即结束和八回合平局。

### 真包黄金测试

从 `server/assent/cfg/paper` 中选择能确定阵容、战法和结果的真实报文，比较：

- 发动阶段和顺序。
- 目标数量与目标阵营。
- 状态类型和持续时间。
- 兵损方向与合理区间。
- 最终胜负。

动画动作和每个随机伤害的精确数值不作为黄金测试要求，除非报文提供了固定随机上下文。

## 分阶段交付

### 阶段一：规则图和覆盖基线

- 建立验收清单生成器。
- 构造完整规则图和依赖校验。
- 建立未知效果、条件和选择器报告。

### 阶段二：效果与状态系统

- 实现 112 种效果处理器。
- 完成冲突、覆盖、叠加、持续、次数和清除规则。
- 迁移现有通用状态。

### 阶段三：触发、条件和目标系统

- 接入完整战斗触发点。
- 实现条件解释器、目标选择器、准备和延迟队列。
- 实现子战法递归。

### 阶段四：特例插件

- 根据剩余覆盖报告实现无法由配置表达的战法。
- 删除与配置解释器重复的 `LegacySkillCatalog` 分支。

### 阶段五：真包校准与交付

- 增加真实报文黄金测试。
- 校准伤害、恢复和状态持续语义。
- 通过全量测试和 `installDist` 构建。

每阶段必须保持出征、战斗结算、占领土地和客户端战报可用，不允许长期分支到最后一次性集成。

## 完成标准

- 308 个目标主战法全部通过战法级测试。
- 668 个执行节点均可到达并执行。
- 112 种效果均有处理器和语义测试。
- 目标范围内 `UnsupportedSkillEffect` 为 0。
- 目标范围内未知条件、未知选择器、断开依赖和无事件主战法均为 0。
- 真包黄金样本的阶段、目标、状态、兵损方向和胜负一致。
- 全量测试与 `installDist` 构建通过。
- 不启动游戏服务，服务启动与客户端实测由用户完成。
