# 已验证语义的正版战报战前投影设计

## 目标

将服务端当前生成的战前战报向 `assent/cfg/paper` 中的正版战报靠拢。本轮只实现能够由真实战报稳定形状、客户端配置或现有反编译代码确认语义的动作，不为追求动作数量而猜测未知协议。

代表样本：

`assent/cfg/paper/11/cap_20260312014510506_0000000b_zlib.json`

该样本使用 `5p`、`0e`、`ba` 和 `8x` 数据重建同阵容并固定随机源后，当前差分基线为：

- 正版战前 625 条动作，83 个动作族；
- 当前生成战前 253 条动作，46 个动作族；
- 双方已有的公共战前动作暂未发现参数宽度差异；
- 当前战前额外出现 `0t/1o/5x/5y/8d`；
- 当前缺少已确认的 `61/66/67` 包络和 `8x/45xxxx` 装备特性链路。

## 范围

### 本轮实现

1. 建立独立的战前协议投影边界，避免 round 0 事件继续复用战中技能包络。
2. 为已确认的战前来源或效果段输出 `66`（开始）、`67`（结束）和 `61`（段边界）。
3. 指挥阶段不再输出正版战前不存在的 `5x/5y/8d/1o` 战中动作。
4. 接通 `BattleHeroSpec.equipmentFeatureSkillIds` 和 `equipmentFeatureSkillLevels`。
5. 为已确认的装备特性输出 `8x`，保留装备、特性技能、关联技能和等级之间的关系。
6. 收紧 `ja` 和 `8c` 的投影条件，只在已有协议依据时输出。
7. 将不能确认的战前效果写入诊断，不伪造客户端动作。
8. 使用真实 `paper` 样本建立自动化差分门禁。

### 本轮不实现

- 语义尚未确认的动作族；
- `3r/44/45/i6/ht/0f/0g/02/5z/i1/i2/hj...hs` 等纯展示或页面编排元数据；
- 尚未确认准确业务分类的 `96 + 281xxx/285xxx`；
- 为单个样本硬编码动作串、阵容或数值；
- 首回合及后续回合的随机结果逐条一致；
- 玩家养成、战后收益、战报持久化等非战前协议工作。

## 方案选择

采用独立战前投影方案，不继续在通用事件投影中堆叠 round 0 分支，也不使用样本模板。

原因：

- 战斗结算事件描述服务端语义，客户端动作描述回放协议，两者不是一一对应关系；
- 正版战前有独立的阶段、来源和包络结构；
- 同一种服务端效果在战前和战中可能使用不同动作；
- 独立边界允许后续按证据逐个增加动作，而不影响战中回放。

## 模型与组件

### 战前投影模型

战前投影至少表达：

- 来源阶段；
- 来源位置；
- 容器来源 ID，例如装备基础 ID；
- 具体效果或特性技能 ID；
- 目标位置；
- 已确认的客户端动作；
- 是否需要 `66/67/61` 包络；
- 无法投影时的诊断信息。

模型不保存任意原始动作字符串。动作仍由类型化字段编码，避免业务代码绕过参数校验。

### FormationCalculator

`BattleFormationCalculator` 负责把队伍配置中的静态来源转成战前事实：

- 普通装备技能继续生成属性、伤害修正和已确认专用动作；
- 装备特性技能从 `equipmentFeatureSkillIds` 和对应等级读取；
- 装备特性保留所属装备基础 ID；
- `8x` 所需的来源位置、特性技能 ID、关联技能 ID 和等级必须来自真实配置或传入规格；
- 没有足够数据时不生成 `8x`。

### 战前编码器

战前编码器负责：

1. 输出来源入口；
2. 为需要包络的效果输出 `66`；
3. 输出一个或多个已确认效果动作；
4. 输出 `67`；
5. 在来源或效果段结束时输出 `61`。

包络顺序由真实样本测试锁定，不根据动作数量推测。

### 指挥阶段

`ClientBattleTextReplayAdapter` 继续负责整场动作顺序，但 round 0 指挥事件交给战前编码器：

- 保留 `05/hw/0m/.../hx` 武将分段；
- 战法发动仍输出 `0m`；
- 属性变化、状态和修正使用战前动作；
- 禁止输出 `5x/5y/8d/1o`；
- 战中 round 1 及以后维持现有投影。

### `ja` 与 `8c`

- `ja` 只表示已经确认可使用该动作的修正效果；
- `8c` 只用于已确认的派生战法或装备附属效果；
- 不能仅凭 `rootSkillId != skillId` 或“无法找到更具体动作”就输出；
- 未确认效果进入诊断，并能在严格测试模式下失败。

## 数据流

```text
客户端/NPC配置
  → BattleHeroSpec
  → BattleFormationCalculator
  → 类型化战前来源与装备特性事实
  → BattleEngine round 0 事件
  → 独立战前投影器
  → ClientReportAction
  → ClientReportTextEncoder
```

战斗引擎不直接生成客户端动作码。

## 错误处理

- 缺少装备基础 ID、特性技能 ID、关联技能 ID或等级时，不生成残缺 `8x`。
- 安全模式记录带来源、效果和阶段的诊断。
- 严格模式抛出 `UnsupportedBattleReportProjectionException`。
- 不允许用 `0` 或空字段伪造必须有真实来源的动作。
- 已确认动作的参数数量和位置范围继续由测试约束。

## 测试策略

### 单元测试

1. 装备特性事实保留基础装备、特性技能、关联技能和等级。
2. `8x` 参数形状与真实样本一致。
3. 包络严格按 `source → 66 → effect → 67 → 61` 输出。
4. 指挥阶段不输出 `5x/5y/8d/1o`。
5. round 1 及以后仍可输出战中技能包络。
6. 未确认效果在安全模式诊断、严格模式失败。
7. `ja/8c` 不再作为未知效果的通用兜底。

### 真实样本差分测试

从代表 `paper/11` 样本读取真实动作并重建同阵容：

- 截取首个 `09x` 之前的战前段；
- 验证生成战前不包含 `0t/1o/5x/5y/8d`；
- 验证生成战前包含 `61/66/67`；
- 验证装备特性包含 `8x` 和 `45xxxx`；
- 比较公共动作族的参数宽度；
- 输出缺失动作族和数量差异作为诊断，但不要求未知动作归零。

差分测试固定随机源，重复执行结果必须一致。

## 完成标准

1. 新增测试均经过红—绿循环。
2. 代表样本的战前错误额外动作 `0t/1o/5x/5y/8d` 清零。
3. 代表样本生成战前具备 `61/66/67`。
4. 代表样本装备特性能够生成真实来源的 `8x/45xxxx`。
5. 公共战前动作参数宽度无新增差异。
6. 全量测试通过；现有技能覆盖门禁的 18 个未知条件属于已知独立缺口，不通过伪造条件规避。
7. 未确认动作没有被猜测性实现。
