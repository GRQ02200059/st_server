# 基础持久同盟创建设计

## 目标

服务端支持玩家创建一个真实、全局持久化的同盟。创建后客户端能够进入同盟主页，显示同盟名称和创建人；服务重启、玩家重登后同盟归属不丢失。

本次不实现申请、邀请、审批、退出、解散、公告编辑或官职管理。

## 客户端协议

- `cmd 102` 接收 `[unionName]`，创建成功时返回一个正的同盟 ID。
- 客户端收到该 ID 后会请求 `cmd 100`，服务端必须返回 `[0, unionInfo]`。
- 同盟主页会请求 `cmd 103`，服务端返回创建人的盟主成员行。
- `unionInfo` 的固定段和字典段必须满足 `UnionData.SetUnionInfo` 的无保护类型读取。
- 创建成功后服务端通过 `cmd 90005` 稀疏更新 `Tb_user`：
  - 字段 `10`: `union_id`
  - 字段 `11`: `union_name`

## 状态与持久化

新增独立的同盟全局状态文件 `data/unions.json`，并复用现有原子写入策略。

每个同盟记录：

- `unionId`
- `name`
- `leaderUserId`
- `leaderRoleName`
- `createdAtSec`
- `memberUserIds`

约束：

- 同盟名按 trim 后的文本唯一。
- 一个玩家最多创建或持有一个同盟。
- 创建人是初始且唯一成员，并以盟主身份返回。
- 同盟 ID 单调递增并从全局状态恢复。

`WorldStateRepository.configure/reset` 同步配置/重置同盟状态，使已有多账号测试使用同一临时数据目录。

## 登录与展示

- `UserInitTableBuilder` 从同盟状态读取当前玩家归属，填充 `Tb_user.union_id` 和 `union_name`。
- `ProfileResponses` 读取相同状态，避免创建后的资料页仍显示“无同盟”。
- 地图同盟标记、申请和成员管理不在本次范围内。

## 错误处理

- 空白名称、超长名称、名称已存在且属于其他同盟时，`cmd 102` 返回 `0`。
- 已在同盟中的玩家重复创建时返回当前同盟 ID，不创建第二条记录。
- 未找到的 `cmd 100` 维持 `[1, []]`，客户端可安全关闭或提示。

## 验证

1. 真实 TCP 回路：登录 -> `102` -> `100`，验证成功状态、同盟 ID 和名称。
2. 创建后 `90005` 包更新 `Tb_user` 的 ID 和名称字段。
3. 同盟服务重建后，创建人仍可通过 `100` 查询同盟。
4. 两名玩家不能用同名创建第二个同盟。
5. 登录快照和资料页显示创建人的同盟。
