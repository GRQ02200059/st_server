# 纯服务端全行军外观解锁设计

## 目标

让本地服务端向真实 9.2.2 客户端解锁全部可授予的行军外观，并保持客户端原有
的选择、绑定、切换、重登恢复和地图渲染路径。实现只修改 Kotlin 服务端，不修改
客户端文件、DLL 或运行时内存。

每种普通行军外观下发 5 张永久卡，可同时绑定 5 名不同的五星武将。用户可在
客户端外观库选择卡片，或在武将详情页切换已经绑定的外观。

## 已确认的客户端事实

- `tb_cfg_army_facade_shop.bin` 是普通行军外观的权威配置来源；当前版本包含 12
  个可通过 `Tb_user_army_facade_card` 分配的外观：
  `101138`、`101156`、`101174`、`101216`、`101239`、`101342`、`101417`、
  `101460`、`101554`、`101565`、`101611`、`101682`。
- 客户端以 `Tb_user_army_facade_card.cfg_hero_id` 表示一张普通外观卡已绑定的
  武将配置 ID，以 `Tb_hero.army_facade_card_id`（字段 72）表示某个武将当前
  使用的行军外观。
- 外观库的批量选择器发送 `682 BATCH_ACTIVE_ARMY_FACADE_CARD`，请求体为
  `[facadeId, heroUidList]`。
- 武将详情页分别使用 `678 UNLOCK_TROOP_FACADE_CARD` 绑定单张未使用卡，
  以及 `677 USE_TROOP_FACADE_CARD` 切换当前外观；两者请求体都是
  `[facadeId, heroUid]`。
- `101073` 禁军由客户端检查是否拥有同 ID 的特殊 `Tb_hero` 外观卡，并通过
  `677` 应用到武将。
- `101515` 西园军、`101618` 西园军玉玺变体和 `101680` 太师方块人使用特殊
  外观卡路径；客户端用 `2520 HERO_ACTIVE_FACADE` 切换其 `Tb_hero.state`。
- 客户端通过行军数据的 `facade_ids` 字符串绘制部队模型。格式为
  `facadeId,position;` 的重复项；当前服务端在 `Tb_army[61]` 和
  `5026[6][armyId][15]` 中均下发空字符串，因此地图不会显示任何行军外观。
- `101681` 是头像而非行军外观。`101155`、`5100` 与 `999991` 没有当前版本中
  可授予的外观实体或属于剧情/主题专用分支，不能伪造成普通已拥有外观。

## 范围

本次实现：

- 基于客户端二进制配置解析 12 个普通行军外观。
- 解锁全部 16 个当前可授予行军外观：12 个普通外观、禁军、西园军、西园军玉玺
  变体及太师方块人。
- 普通外观每种 5 张永久卡，并支持 `682`、`678`、`677`。
- 特殊外观卡的登录投影、`2520` 状态切换与持久化。
- 登录、90005、Tb_army 和 5026 四个投影的一致性。
- 出征时向客户端写入按部队位置编码的行军外观，使地图模型真实变化。

本次不实现：

- 行军外观的商城购买、活动资格、轮换池、过期时间或消耗逻辑。
- 外观卡的赠送、交易、回收与服务端活动排行。
- 客户端主题开关和地图模式伪造。`101618` 的公平地图表现和 `101680` 的主题服务器
  表现仍受客户端自身条件约束；服务端负责解锁、保存和下发，不强制绕过客户端渲染
  限制。

## 架构

### 外观目录

新增 `ArmyFacadeCatalog`，作为行军外观的唯一目录边界。

- 将 `tb_cfg_army_facade_shop.bin` 随服务端资源打包到 `client-config/`。
- 使用已有 `MemoryPackTable` 解析键和每行 9 字段，读取并校验 `heroid`。
- 普通外观目录按配置顺序返回去重、正数 ID；解析失败或为空时立即失败，不退回到
  容易过时的硬编码列表。
- 特殊目录固定为 `101073`、`101515`、`101618`、`101680`，并有明确的客户端
  所有权类型和激活协议。
- 所有命令和状态归一化只接受这个目录中的 ID。

### 玩家状态

`PlayerState` 成为外观所有权的唯一持久化来源，新增：

- 普通卡记录：稳定卡实例 ID、外观 ID 和已绑定的武将配置 ID，`cfgHeroId=0`
  表示未使用。
- 每个可出战 `PlayerHero` 的 `armyFacadeCardId`，默认 `0`。
- 特殊卡记录：外观 ID、稳定的客户端外观卡 UID 和启用状态。

普通卡的初始化规则是每个配置外观固定 5 张。卡的稳定 ID 由外观 ID 与副本序号
计算，且不复用可出战武将 UID。特殊卡 UID 使用独立的保留 UID 工厂，并在生成时
检查不与任一可出战武将 UID 冲突。

恢复旧存档时，缺失字段按以下规则归一化：

1. 补齐每种普通外观至 5 张，保留已有卡实例与绑定。
2. 补齐 4 张特殊卡，默认未启用。
3. 移除目录外的普通卡。
4. 清除引用不存在、非五星、非可出战武将的绑定。
5. 同一普通外观不能重复绑定同一武将配置；按稳定卡 ID 保留第一张，其余解绑。
6. 武将当前外观若没有对应的已绑定普通卡，且不是禁军，清为 `0`。

### 客户端投影

99991 登录快照包含：

- `Tb_user_army_facade_card`：普通外观共 60 行。字段
  `[2]=facade_heroid`、`[5]=cfg_hero_id` 来自普通卡记录。
- `Tb_hero[72]`：每名可出战武将当前行军外观。
- `Tb_hero` 特殊外观卡：禁军、西园军、西园军玉玺变体和太师方块人以独立、不可
  出战的外观卡行下发；`[5]=state` 反映特殊卡是否启用。
- `Tb_army[61] facade_ids`：将该队当前出战武将按位置序列化为
  `facadeId,position;`。未设置时为空字符串。

`GameResponses.worldSceneFullInfo` 用同一序列化器在 5026 的第 15 槽写入
`facade_ids`。`PlayerMarchHero` 捕获发兵时的 `armyFacadeCardId`，以保证行军
途中显示和出征时选择一致。

特殊外观启用后，服务器将它作为该账号当前有效的全局特殊行军外观，在 5026 中
覆盖对应位置的普通外观。禁军仍遵从武将级选择；西园军和其变体遵从客户端特殊卡
语义。若客户端因主题或地图条件不渲染某项外观，服务器保持状态但不伪造额外条件。

## 命令和同步

`Cmd` 增加：

- `USE_TROOP_FACADE_CARD = 677`
- `UNLOCK_TROOP_FACADE_CARD = 678`
- `BATCH_ACTIVE_ARMY_FACADE_CARD = 682`
- `HERO_ACTIVE_FACADE = 2520`

### 普通外观操作

`682 [facadeId, heroUidList]`：

1. 解析数组，去重后保持客户端请求顺序。
2. 验证 `facadeId` 是普通目录项，目标均为该玩家拥有的五星可出战武将，并且同一
   武将配置没有重复目标。
3. 验证未绑定卡数量足够。
4. 为每个目标取一张稳定排序后的未绑定卡，写入目标武将配置 ID，同时设置每名目标
   武将的当前外观为 `facadeId`。

`678 [facadeId, heroUid]` 使用同一分配规则处理一个目标。

`677 [facadeId, heroUid]`：

- `facadeId=0` 将目标武将恢复默认。
- 普通外观只能切换到已绑定给该武将配置的卡。
- 禁军只能在已拥有禁军特殊卡时切换。
- 不重新分配或销毁普通卡。

每个成功操作按稳定顺序发送：

1. 原命令号的 `[]` 响应。
2. 保存状态。
3. 一条 `90005`，先更新受影响的 `Tb_user_army_facade_card[5]`，再更新按武将
   UID 升序排列的 `Tb_hero[72]`。
4. 对受影响队伍更新 `Tb_army[61]`，并在有行军时立即下发 5026。

### 特殊外观操作

`2520 [specialCardUid, state]` 只接受西园军、西园军玉玺变体或太师方块人的
当前账号特殊卡 UID，且 `state` 为 `0` 或 `2`。它更新相应特殊卡的启用状态，并
确保同一特殊外观槽位只有一张卡处于启用状态。禁军不接受 `2520`，只能通过 `677`
应用到武将。成功时返回原命令、保存状态、以 90005 更新特殊 `Tb_hero[5]` 并刷新
受影响的 5026 行军数据。

不实现客户端未验证的活动资格校验；所有 4 张特殊卡永久可用。

## 错误处理

以下情况不改变状态：

- 请求不是所需数组形状、ID 非正数或 `state` 不在允许集合。
- 外观 ID 不在对应目录中。
- 目标武将不存在、不是五星、不可出战，或不属于当前玩家。
- 同一请求包含重复 UID、同一武将配置重复，或普通卡数量不足。
- `677` 请求一个未绑定给目标武将的普通外观。
- `2520` 请求非当前账号拥有的特殊卡 UID。
- 请求已经与当前状态完全相同。

所有无效或无变化请求保持既有服务端约定：回原命令的 `[]`，不保存且不发送
90005。服务端用结构化日志记录拒绝原因，不伪造未验证的客户端错误码。

## 测试

测试先行，覆盖以下层次：

1. `ArmyFacadeCatalogTest`
   - 解析真实二进制配置得到精确的 12 项普通外观。
   - 目录包含 4 项特殊外观并明确排除 `101681`、`101155`、`5100` 与 `999991`。
2. `PlayerStatePersistenceTest`
   - 新账号产生 60 张普通卡和 4 张特殊卡。
   - 682 批量绑定、678 单张绑定、677 切换与恢复默认。
   - 同种外观最多 5 张、同一配置武将不可重复绑定、无效目标无状态变化。
   - 特殊卡切换、旧存档归一化和重登恢复。
3. `UserInitTableBuilderTest`
   - 快照的普通卡数量、字段位置和绑定状态准确。
   - `Tb_hero[72]`、特殊卡 `Tb_hero[5]`、`Tb_army[61]` 与状态一致。
4. `GameResponsesTest`
   - 90005 的更新表、字段索引和确定性顺序准确。
   - 5026 的第 15 槽使用 `facadeId,position;`，无外观时为空。
5. `GameServerHandlerProtocolTest`
   - 677、678、682 和 2520 的成功响应、90005 与持久化。
   - 非法请求没有 90005，且重登后状态未变化。
   - 正在行军时切换外观会重发正确的 5026。

最终验证运行相关测试、`installDist` 和产物 SHA-256 校验。部署到 `59979` 后，
用真实客户端验证普通卡批量绑定、武将详情切换、特殊卡启用、出征模型和重登恢复。
已有的无关全量测试失败将单独列出，不作为本功能失败。
