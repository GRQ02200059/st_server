# 玩家账号数据持久化设计

## 目标

让服务端在断线重连和进程重启后恢复同一玩家的账号、角色、资源、建筑、武将、队伍与进行中的行军数据。首次运行不引入数据库，使用本地 JSON 文件完成单机/私服部署所需的可靠持久化。

## 范围

本阶段包含：

- 稳定的账号键与 `userId` 映射。
- 账号基础信息：角色名、主城、创建/登录时间。
- 玩家资源、建筑等级。
- 武将实例：UID、配置 ID、等级、兵力、体力、兵种类型、部队归属、创建时间。
- 三个队伍槽位。
- 进行中的单支行军。
- JSON 存档加载、保存、损坏文件保护和旧字段默认值。
- 登录快照从恢复后的 `PlayerState` 生成。

本阶段不包含：

- 多进程并发写入。
- 多玩家世界同步。
- 战斗规则补全。
- 战报历史的独立持久化。
- 数据库迁移。

## 持久化方案

存储根目录由 `STZB_DATA_DIR` 指定；未设置时使用当前工作目录下的 `data`。每个账号一个文件：

```text
data/
  accounts/
    <account-key>.json
```

账号键只允许 ASCII 字母、数字、`.`、`_`、`-`，其他字符使用 SHA-256 编码后作为文件名，避免路径穿越。

写入采用：

1. 将完整快照写入同目录临时文件。
2. `fsync` 文件内容。
3. 原子移动临时文件覆盖目标文件。
4. 保留最近一次损坏/无法解析的原文件为 `.corrupt.<timestamp>`，当前请求使用默认新状态继续运行。

## 领域模型

`PlayerState` 继续作为运行时可变模型；新增稳定的 `accountKey`，并提供完整快照导出/恢复能力。持久化层不直接依赖 Netty。

```kotlin
interface PlayerRepository {
    fun findByAccount(accountKey: String): PlayerState?
    fun getOrCreate(accountKey: String, cityWid: Int, roleName: String): PlayerState
    fun save(state: PlayerState)
}
```

`FilePlayerRepository` 负责 JSON 编解码和文件操作；`PlayerStateRepository` 作为现有调用方兼容入口，内部委托文件仓储。

## 账号绑定

登录流程使用客户端请求中稳定的登录账号标识作为 `accountKey`。如果当前客户端请求无法提供稳定标识，则使用固定开发账号键 `local-dev-account`，保证本地 `adb reverse` 重连仍回到同一存档。

首次创建账号时分配永久 `userId`，写入账号文件；以后连接只根据账号键读取该 `userId`，不再在 `channelActive` 时每次递增。武将 UID 由存档内的 `heroSeq` 继续递增，避免重启后复用 UID。

## 保存触发点

以下状态变化完成后立即保存：

- 创角/角色名变更。
- 招募武将。
- 上阵、下阵、换位、保存队伍。
- 征兵。
- 建筑升级。
- 出征扣除体力、创建行军。
- 行军结算后的兵力、行军状态和战报引用状态。

保存失败不得静默吞掉：记录错误并保留内存状态；下一次保存继续尝试。

## 兼容与恢复

- 缺失的 JSON 字段使用当前默认值。
- 缺失或非法的英雄类型重新从 `HeroCatalog` 推导。
- 缺失的队伍槽位补零。
- 没有行军时使用 `null`。
- 旧的只有运行时内存状态的进程升级后，第一次保存生成新格式文件。

## 验收标准

1. 同一个 `accountKey` 两次加载得到相同 `userId`。
2. 招募的武将 UID、英雄 ID、兵力、体力、等级和队伍位置在重新加载后保持不变。
3. 资源和建筑升级在重新加载后保持不变。
4. 进行中的行军在重启/重新构造仓储后仍可读取，并能按结束时间结算。
5. 损坏存档不会覆盖原文件，且新状态可正常创建。
6. `99991` 登录快照包含恢复后的武将、队伍、资源和建筑。
7. 现有战斗、招募、协议测试继续通过。
