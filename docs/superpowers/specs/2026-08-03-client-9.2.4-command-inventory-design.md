# Client 9.2.4 Command Inventory Design

- Date: 2026-08-03
- Target package: `com.netease.stzb.netease`
- Target package version: `9.2.4` (`versionCode=3818002`)
- Managed assembly version: `1836157`
- Decision: use the recommended option under the user's standing
  authorization to proceed without interactive confirmation.

## Goal

Replace the server's active 9.2.2 command catalog with an inventory generated
from the currently installed 9.2.4 client, while preserving the 9.2.2 file as
historical evidence.

This change inventories commands only. It does not claim official response
shapes and does not add provisional handlers for newly discovered commands.

## Evidence

The current device Assembly directory was pulled through
`adb -s 127.0.0.1:5555` without starting or restarting the client. Four patched
assemblies were replaced by their pre-deployment backups from
`20260802014717`, all 34 managed assemblies were normalized with the existing
`normalize_pe_sections` helper, and ILSpy produced 17,458 C# files.

The resulting scan found:

- 2,655 inventory command IDs.
- 1,779 `CLIENT_REQUEST`, 307 `DUPLEX`, and 569 `SERVER_PUSH` commands.
- 4,144 resolved request sites and 525 resolved receive sites.
- 96 unresolved request sites retained for later audit.
- 63 inventory IDs added and 2 removed relative to 9.2.2.
- 64 new constants in `NetCommandDef`; cmd 8009 already existed through
  capture evidence and now gains the official name `WORLD_BOSS_RANKING_LIST`.
- All 9.2.4 capture counts are initially zero because the client process was
  not running and the existing capture index belongs to earlier client
  versions.

No game command was sent while collecting this evidence.

## Options

### Selected: versioned resources

Keep `client-9.2.2-command-inventory.json`, add
`client-9.2.4-command-inventory.json`, and make 9.2.4 the explicit runtime
resource. This preserves provenance and makes the active client version
unambiguous.

### Rejected: overwrite the 9.2.2 resource

This has a smaller diff but destroys the historical evidence boundary and
makes old commits impossible to reproduce from their named resource.

### Rejected: runtime multi-version auto-selection

The server currently targets one client build. Adding environment-driven
selection would introduce configuration and test branches without a current
consumer.

## Design

### Generator

`tools/client_protocol_inventory.py` accepts an explicit client version and
passes it to `build_inventory`. The CLI requires `--client-version`; there is
no implicit version that can silently label evidence incorrectly.

The scanner continues to consume:

1. A decompiled client root.
2. `Game.Network/Tenth.Network/NetCommandDef.cs`.
3. Every C# request and observer site under that root.
4. An optional, same-version capture index for runtime counts.

When `--capture-index` is omitted, the generator uses an empty capture map.
The initial 9.2.4 resource is generated this way. The mixed historical
`samples/protocol/index.json` must not be supplied for 9.2.4: doing so would
incorrectly transfer old capture counts and direction evidence into the new
catalog.

### Runtime

`CommandContractRegistry.loadFromClasspath(version)` supports the preserved
9.2.2 resource and the new 9.2.4 resource, and validates that the embedded
`clientVersion` matches the requested version. `CommandContractCatalog`
explicitly selects 9.2.4 as the active runtime inventory.

The registry remains inventory-driven: every inventory entry gets one
effective contract, and explicit overrides must refer to an inventory ID.
`Cmd.kt` remains the readable constant set for commands used by production
code; it is not expanded mechanically to every inventory row.

`CommandCoverageReport` reads the active version from the registry instead of
embedding `9.2.2` in its heading. The Gradle task description is updated to
match the active version.

### Compatibility

The two 9.2.2-only IDs, 4279 and 6032, have no production override or handler
reference and can disappear from the active catalog. Existing overrides are
otherwise preserved. Newly discovered commands enter as `UNIMPLEMENTED`
until a captured response or independently justified rejection is available.

No newly discovered command is added to generic fallback response sets.

## Error Handling

- Reject an inventory whose embedded version does not match the active
  version.
- Reject unsupported classpath inventory versions.
- Reject duplicate command IDs.
- Reject explicit contract overrides absent from the active inventory.
- Keep unresolved request sites in the generated artifact instead of
  guessing their command IDs.
- Fail generation when `NetCommandDef.cs` or a supplied capture-index path is
  missing.
- Do not merge capture counts unless the supplied index is known to come from
  the same client version.

## Tests

### Python

- Verify explicit 9.2.2 and 9.2.4 versions appear in generated JSON.
- Verify an omitted capture index produces zero capture counts.
- Verify command ordering, uniqueness, source discovery, and capture merging
  remain deterministic.

### Kotlin

- Verify the classpath inventory reports 9.2.4 and contains 2,655 unique,
  sorted IDs.
- Verify both versioned resources can be loaded explicitly and an unsupported
  version is rejected.
- Verify representative 9.2.4 additions from new-player, domestic, alliance,
  ranking, and season domains are present with their names and inferred
  directions.
- Verify the production registry has exactly the active inventory ID set.
- Verify the coverage report starts with `# 9.2.4 Command Coverage`.
- Re-run the four focused protocol suites and `protocolCoverageReport`.

## Non-Goals

- Starting or restarting the Android client.
- Sending official-server requests while the client process is absent.
- Implementing responses for the newly discovered commands without captured
  response evidence.
- Removing or rewriting the historical 9.2.2 inventory.
