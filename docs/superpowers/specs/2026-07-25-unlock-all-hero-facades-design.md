# 全部武将画像解锁设计

## 目标

让客户端中所有普通武将画像和成就武将画像均显示为已拥有，并可在已有武将卡的外观界面中选择、更换。画像选择需要跨重启持久化。

本功能不修改武将成就进度，不授予成就附带的头像、头像框、登录主题或其他奖励，也不额外创建武将卡。

## 客户端契约

客户端通过 `Tb_user_facade_card` 判断画像是否已拥有：

- `facade_heroid` 对应画像配置 ID。
- `base_heroid` 对应可使用该画像的基础武将配置 ID。
- `end_time = 0` 表示永久有效。
- `read = 1` 避免生成批量未读红点。
- `gain_type = 0` 避免进入赠礼画像逻辑。

客户端画像列表仍由本地配置决定。服务端只下发所有有效画像的拥有记录，不修改客户端配置的赛季、资源或展示关系。

画像切换后，客户端依赖 `Tb_hero.dynamic_icon` 展示当前画像。因此服务端必须校验画像与武将的绑定关系，保存选择，并下发更新后的完整 `Tb_hero` 行。

## 数据来源与筛选

服务端新增画像目录模块，读取已有的 `hero_table.csv`：

1. 只选择画像类型的配置行，不选择普通可招募武将。
2. 画像配置必须具有有效画像 ID 和至少一个基础武将绑定。
3. 同一画像关联多个基础武将时，为客户端生成其配置关系允许的拥有记录。
4. 普通画像和成就画像使用同一拥有表，因此统一生成 `Tb_user_facade_card`。
5. 无法解析或缺少基础武将关系的配置行跳过并记录诊断信息，避免下发无效 ID 导致客户端空引用。

筛选逻辑由测试使用已知普通画像、已知成就画像和普通武将行固定。

## 登录数据

`UserInitTableBuilder` 在 `Tb_user_facade_card` 表中加入所有画像拥有记录。每条记录使用稳定且唯一的 ID，保证同一账号每次登录行键不变。

不生成或篡改 `Tb_hero_achieve`。这样成就界面仍显示真实进度，但成就奖励画像可在武将外观界面直接使用。

## 切换与持久化

玩家存档为每个武将实例保存当前画像 ID，默认值为 `0`。

切换请求处理流程：

1. 从登录会话解析账号存档，禁止回退到另一份 legacy 存档。
2. 解析武将 UID 和目标画像 ID；`0` 表示恢复默认画像。
3. 验证武将属于当前账号。
4. 验证目标画像存在，且其基础武将关系与该武将配置匹配。
5. 更新武将 `dynamicIcon` 并保存存档。
6. 返回客户端期望的成功响应。
7. 下发该武将的 `Tb_hero` 更新通知。

非法画像或不匹配的画像不会写入存档，也不会让 `Tb_hero` 引用不存在的客户端配置。

## 非目标

- 不修改成就等级、积分、排行、票券或领奖状态。
- 不解锁专属头像、头像框、登录主题、动态视频之外的附属奖励。
- 不修改武将卡持有数量。
- 不实现画像购买、赠送、限时过期或轮换池业务。
- 不修改客户端资源文件。

## 测试与验收

自动化测试覆盖：

- 目录同时包含已知普通画像和成就画像，并排除普通武将。
- 登录表为全部画像生成永久、已读、非赠礼拥有记录。
- 画像拥有记录 ID 稳定且唯一。
- 合法画像可切换并持久化到 `PlayerStateSnapshot`。
- 默认画像可恢复。
- 不属于该武将或不存在的画像被拒绝。
- `Tb_hero.dynamic_icon` 使用已保存的画像 ID。
- 登录初始化不伪造 `Tb_hero_achieve`。
- 全量测试和 `installDist` 构建通过。

客户端验收：

1. 重启服务并重新登录。
2. 打开任意已拥有武将的外观界面。
3. 普通画像和成就画像均显示可用。
4. 选择后卡面立即更新。
5. 重新登录后仍保持选择。
6. 成就进度和附属奖励未被改动。
