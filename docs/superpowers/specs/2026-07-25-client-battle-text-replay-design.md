# 客户端战斗文字回放设计

## 目标

将现有 Kotlin `BattleEngine` 产生的 `BattleResult` 和 `BattleEvent` 接入客户端
`cmd=11` 战报详情，使客户端能稳定显示完整的文字战报时间线：

- 一个准备回合；
- 引擎实际执行的 1 至 8 个回合；
- 普通攻击和技能伤害；
- 恢复、状态施加、持续伤害、规避和属性变化；
- 最终兵力和胜负。

战报回放的唯一结算来源是 `BattleEngine`。协议适配层不得重算伤害、恢复、状态持续时间或胜负。

## 范围

本轮只实现文字回放，不实现战斗视频回放。

明确不包含：

- `BattleAnimationData` 消费的镜头、角色移动、特效或受击动画分组；
- 原服专属战法表现、素材、音效和镜头节奏；
- 为未支持战法补造原服动画协议。

文字回放仍使用客户端标准 `cmd=11` 的 `report` 动作流。服务端继续发送
`zzz + Base64(GZip)` 格式；客户端的 `ReportDetailData.CheckZip()` 已支持该格式。

## 客户端约束

客户端先将每条记录的前两个 base36 字符还原为动作 ID，再交由
`ReportDetailHelper` 解析。动作 ID 必须存在于客户端的 `ReportDetailCfg.ActionDescDict`，
否则该记录会被客户端直接忽略。

回合栏由 `ReportDetailView.AnalyzeDetails()` 建立：

- 动作 `04` 只接受第一次出现，代表准备阶段；
- 动作 `09` 每出现一次即建立一个后续回合；
- 继续发送多个 `04` 会被客户端忽略，正是当前只有一个准备回合的根因。

因此协议输出必须保证：

1. 全战斗仅出现一个 `04`；
2. 每个引擎 `RoundStart(round)` 恰好对应一个 `09<round>`；
3. 不再把所有语义事件编码成 `0u`（动作 `30`）；
4. 每条业务记录使用真实 `cmd=11` 样本和客户端代码验证过的动作族与参数布局。

## 架构

新增独立的 `ClientBattleTextReplayAdapter`，替换现有直接拼接动作号的
`ClientReportTextEncoder` 实现。

```text
BattleEngine
    -> BattleResult / BattleEvent
    -> ClientBattleTextReplayAdapter
    -> ClientReportAction records
    -> ClientReportTextEncoder
    -> BattleReportCodec (GZip + Base64)
    -> cmd=11 report
```

### `ClientBattleTextReplayAdapter`

适配器只负责从引擎事件投影为客户端可显示的文字动作。它由三个阶段组成：

1. **开场阶段**
   - 发送经客户端验证的武将映射和初始资料记录；
   - 发送唯一的 `04` 准备回合记录；
   - 不发送动画开始、镜头或特效分组记录。
2. **回合阶段**
   - 每次 `RoundStart` 发送 `09<round>`；
   - 每个事件映射为带类型的 `ClientReportAction`，而非散落的整数和可变参数；
   - 只写入文字详情展示所需的动作，不依赖视频回放动作。
3. **结算阶段**
   - 将每名双方武将的结算兵力写入客户端认可的最终兵力记录；
   - 写入与摘要和地图部队结果一致的胜负文字记录；
   - 不额外发送 `09` 伪造回合。

### `ClientReportAction`

内部动作记录应封装：

- 已验证的动作 ID；
- 来源和目标的客户端位置索引；
- 战法 ID、效果 ID、数值和回合；
- 固定的参数顺序；
- 对应的引擎事件类型。

所有动作 ID 和参数形状维护在一个集中协议表中。协议表的每项必须能指向：

- `paper.zip/0000000b` 的真实样本；
- `ReportDetailHelper` 或 `BattleAnimationData` 的客户端解析证据；
- 一条适配器回归测试。

适配器支持以下事件投影：

| 引擎事件 | 文字回放内容 |
| --- | --- |
| `NormalAttack` | 攻击者、目标、伤害、目标剩余兵力 |
| `SkillDamage` | 技能名称、效果、目标、伤害、目标剩余兵力 |
| `Recovery` | 技能或效果、目标、恢复数量、目标剩余兵力 |
| `StatusApplied` | 来源、目标、状态、持续回合 |
| `OngoingDamage` | 持续状态、目标、伤害、目标剩余兵力 |
| `Evaded` | 来源、目标、规避结果 |
| `StatChanged` | 来源、目标、属性变化值和持续回合 |
| `UnsupportedSkillEffect` / `UnsupportedEquipmentEffect` | 保留在服务端 JSON 战报中；文字战报只产生经验证的安全说明记录，不伪装为伤害 |

## 协议与降级规则

1. 普通攻击、战法伤害、恢复、状态和持续伤害分别映射到不同的客户端动作族。
2. 无真实样本和客户端解析证据的动作不得发送。
3. 无法映射的视频专属信息直接省略，不影响对应的文字事件。
4. 未支持的引擎效果不得复用伤害动作，不得使用统一的 `0u` 占位。
5. 客户端位置保持既有映射：攻击方为 `1..3`，防守方为 `4..6`。
6. 最终兵力必须来自 `BattleResult` 的结算队伍，不得从事件流倒推。
7. `cmd=10` 摘要、`cmd=11` 详情、`Tb_battle_report_attack` 和地图战斗结果使用同一个
   `BattleOutcome` 映射来源。

## 错误处理

- 事件中的位置不在 `0..2`：适配器抛出受控错误并拒绝生成损坏战报。
- 引擎事件缺少客户端可用的关键 ID：该事件不写入客户端动作流，但保留在
  `BattleReportCodec.toJson()` 的完整服务端战报中。
- 适配器输出空动作流：写入唯一准备回合和结算文本，保证客户端战报页可打开。
- 任何未知客户端动作：测试失败，禁止进入生产输出。

## 测试策略

### 协议单元测试

- 一个战斗结果只生成一次 `04`；
- 引擎有 N 个 `RoundStart` 时，输出恰有 N 个 `09`，且回合号顺序为 `1..N`；
- 普攻、技能伤害、恢复、状态和持续伤害使用不同的已验证动作族；
- 输出不包含通用 `0u` 占位记录；
- 输出位置索引、技能 ID、效果 ID、伤害值、恢复值和剩余兵力与 `BattleEvent` 一致；
- 结算记录与 `BattleResult` 双方最终兵力和胜负一致。

### 抓包回归测试

- 将 `paper.zip/0000000b` 的动作记录解码为 base36 ID；
- 协议表中的每个客户端动作 ID 都必须出现于真实样本，或有明确的客户端解析分支；
- 测试记录真实样本的开场 `04` 和后续多个 `09` 结构，防止再次退化为多个准备回合。

### 集成测试

- 使用真实英雄和战法生成一场 seeded 的 1 至 8 回合战斗；
- 解压 `zzz` 战报，断言文字动作流包含所有引擎支持事件；
- 验证 `cmd=11` 的压缩格式、`cmd=10` 摘要以及战斗结算兵力保持一致。

### 真机验收

1. 出征后等待 3 秒结算。
2. 从战报列表打开详情。
3. 可见准备回合和实际执行的 1 至 8 回合。
4. 文字列表包含攻击、技能、伤害、恢复、状态和胜负。
5. 关闭战报详情和返回战报列表不崩溃。

## 验收标准

- 客户端不再只显示一个准备回合。
- 每场战斗显示引擎实际执行的所有回合，最多 8 个。
- 文字明细中的数值与 `BattleEngine` 事件和最终兵力一致。
- 不发送 `0u` 通用占位动作。
- 战报详情、战报列表和关闭流程在真机上稳定。
- `./gradlew test --no-daemon -Dkotlin.compiler.execution.strategy=in-process` 通过。
